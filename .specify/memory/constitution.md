# Constitution for Merkle Airdrop

## Preamble

This document outlines the core principles, standards, and governance for the Merkle Airdrop project. Adherence to this constitution is mandatory for all contributors to ensure consistency, quality, and maintainability of the codebase and related artifacts.

---

## Governance

- **Ratification Date**: 2025-11-19
- **Last Amended**: 2025-11-19
- **Constitution Version**: 1.0.0

### Amendment Process

Amendments to this constitution require a consensus among the core development team. Proposed changes must be submitted as a pull request, detailing the rationale and impact.

### Versioning

This constitution follows semantic versioning (`MAJOR.MINOR.PATCH`):
- `MAJOR` versions for incompatible changes or removal of principles.
- `MINOR` versions for adding new principles or significant expansions.
- `PATCH` versions for clarifications, typo fixes, or minor edits.

---

## Principles

### Principle 1: Technology Stack

**All development MUST adhere to the specified technology stack.**

- **Solidity Version**: Smart contracts MUST be written in Solidity `0.8.20`.
- **Framework**: The project MUST use the `Foundry` framework for development, testing, and deployment.

*Rationale: Standardizing the technology stack prevents compatibility issues and ensures that all contributors work within a consistent and predictable environment.*

### Principle 2: Code and Documentation Standards

**Code and documentation MUST be clear, professional, and accessible.**

- **Language**: All code comments, function names, variable names, and documentation MUST be written in English.
- **README**: The project MUST maintain a high-quality `README.md` file, written in English, that is comprehensive and follows the conventions of a well-regarded open-source project. It should clearly explain the project's purpose, setup, and usage.

*Rationale: Consistent use of English and high-quality documentation are essential for attracting contributors, ensuring maintainability, and making the project accessible to a global audience.*

### Principle 3: Project Structure and Architecture

**The project MUST maintain a clean, logical, and modular structure.**

- **Directory Structure**: The project MUST follow the standard directory structure conventions of the Foundry framework.
- **Architectural Design**: Code MUST be designed with the principles of single responsibility, high cohesion, and low coupling. Smart contracts and other modules should be focused and have a clear, distinct purpose.

*Rationale: A well-organized and modular architecture improves code readability, simplifies maintenance, and makes the system easier to test and extend.*

### Principle 4: Communication Language

**Communication mediums have designated languages to ensure clarity.**

- **Conversational Interaction**: All interactive chat and discussions (e.g., with CLI agents or team members) SHOULD be conducted in Chinese.
- **Technical Artifacts**: All code, comments, documentation, and generated files MUST be in English.

*Rationale: This bilingual approach allows the development team to communicate efficiently in their native language while ensuring the project's technical artifacts are universally understandable.*
